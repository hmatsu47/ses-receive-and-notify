# Requirements — SES受信メールのSlack通知ツール

> 上流トレース: `../../ideation/intent-capture/intent-statement.md`（意図・成功基準）、`../../ideation/scope-definition/scope-document.md`（スコープ境界）、`../practices-discovery/team-practices.md`（慣習・テスト方針）。FR/NFR の ID は恒久的なトレーサビリティキーであり、後続ステージはこれを維持する。

## Intent Analysis（意図分析）

- 送信ドメインのレピュテーション向上のためMXを登録しSESで受信サーバーを構築するにあたり、原則受信しない当ドメインへ稀に届くメールを**取りこぼしなく**保管・通知することが目的（`intent-statement.md`）。
- 単独開発・単独運用の小規模ツール。受信は1日数通（いたずら時でも数十通）程度で、高負荷対策より信頼性・可視性を優先する（`intent-statement.md`）。

## Functional Requirements（機能要件）

### FR1 受信とS3保存
- **FR1.1** SES受信ルールにより、対象ドメイン宛の受信メールを1st S3バケットに原本（raw）として保存する。
- **FR1.2** 1st S3バケットへのオブジェクト作成（ObjectCreated）イベントをトリガにデコードLambdaを起動する（S3イベント駆動）。

### FR2 デコードと2nd S3保管
- **FR2.1** Lambdaは1st S3バケットの原本を取得し、本文（プレーンテキスト／HTML）と添付ファイルをデコードする。
- **FR2.2** デコード結果を2nd S3バケットへ整理保管する。オブジェクトキーは受信年月日（時分）＋メッセージIDで構成し、受信日時でソート可能な形式とする（`buildObjectKey` に集約。例: 受信日時プレフィックスを先頭に置きソート順＝時系列となるキー設計）。
- **FR2.3** 保管する本文の先頭に、受信年月日（時分）・エンベロープFrom・Subject・From等の各種ヘッダを本文の前に付与する。
- **FR2.4** 添付ファイルの合計サイズが処理上限（合計10MB）を超える場合、添付のデコードをスキップする。この場合も原本保存と後続のSlack通知は継続する。
- **FR2.5** 冪等キーはオブジェクトキー全体（受信年月日＋メッセージID）とする。同一のオブジェクトキー（＝同一受信日時かつ同一メッセージID）に対しては2nd S3への重複保管を行わない。なお、同一メールが何らかのトラブルで異なる受信日時タイムスタンプで再到達し二重記録される稀なケースは、影響が軽微であるため許容する（日時ソート可能なキーにより時系列で識別できる）。

### FR3 Slack通知
- **FR3.1** デコード・保管後、単一のSlack Webhook URL（.env指定）を用いて単一チャネルへ通知する。
- **FR3.2** 通知には、受信年月日（時分）・Subject・本文概要・保存先S3リンクを含める。受信日時とSubjectは本文（概要）の前に記載する。
- **FR3.3** 本文概要は、デコード済みプレーンテキスト本文（HTMLメールはテキスト抽出後）の冒頭200文字程度とする。付与したヘッダは概要の文字数に含めない。
- **FR3.4** 保存先S3リンクは s3:// 形式パスまたはコンソールURL（参照情報。実アクセスはIAM権限保有者のみ）とする。presigned URLは用いない。
- **FR3.5** 同一のオブジェクトキー（受信年月日＋メッセージID）に対してSlack通知を重複発火させない（オブジェクトキー単位で冪等）。

### FR4 設定の外部化
- **FR4.1** 対象ドメイン・外部リソース（手動作成分等）・Slack Webhook URL等の設定値は、.envまたはSecrets Manager経由で読み込む（ソースへのハードコード禁止）。

### FR5 失敗ハンドリングと可視化
- **FR5.1** 受信・デコードの失敗は CloudWatch Logs で可視化する。
- **FR5.2** デコード失敗時も受信メールの原本S3保存は継続する。Slack送信失敗時も保存は継続する（部分失敗継続）。
- **FR5.3** Lambdaの自動リトライを用い、リトライ後も継続できない処理はデッドレターキュー（DLQ）へ退避してCloudWatch Logsで可視化する。

## Non-Functional Requirements（非機能要件）

- **NFR1 信頼性**: 受信したメールは必ず原本保存され、必ず（オブジェクトキー＝受信日時＋メッセージID単位で一度）Slack通知される（取りこぼしゼロ）。部分失敗（デコード不能・添付上限超過・Slack送信失敗）が起きても原本保存は失われない。合否基準: 冪等性テスト・部分失敗継続テスト・失敗注入テストが全緑（`team-practices.md`）。
- **NFR2 可観測性**: 受信・デコード・通知の失敗はCloudWatch Logsに記録され、DLQに退避された項目が確認できる。合否基準: 失敗注入時にログ出力とDLQ退避が確認できる。
- **NFR3 セキュリティ**: 秘匿値（Webhook URL等）・PIIをソース/IaC/ログ/監査に平文で残さない。Lambda IAMは最小権限（対象S3の get/put、CloudWatch Logs、必要な SSM/Secrets に限定）。合否基準: IAMポリシーが最小権限で、ログ・監査に秘匿値/PIIが出力されない。
- **NFR4 スケーラビリティ（軽量）**: 受信は1日数通（ピークでも数十通）程度を前提とし、特別なスケーリング設計は要さない。標準的なLambda同時実行で十分。
- **NFR5 テスタビリティ**: 外部依存（SES/S3/Slack Webhook）はアダプタ越しに扱い、ユニットテストでモック/スタブ可能とする。実AWS資格情報なしでローカル/CIから無認証実行可能に保つ（`team-practices.md`）。

## Constraints（制約）

- 実装言語は TypeScript/Node（AWS Lambda）＋ AWS CDK を第一候補とし、支障時はPythonへ切替（`team-practices.md`）。
- Route53のドメイン/レコード登録・SESドメイン検証は手動運用（同一/別AWSアカウント両対応。別アカウント連携は既存実装 dmarc-report-visualizer を参照）。
- デプロイは単一環境・IaC手動デプロイ・自己承認（`team-practices.md`）。

## Assumptions（前提）

- 処理上限の合計10MBは、Lambda実行環境（メモリ/一時領域/実行時間）に十分収まる値として設定する。設計で実行環境設定と整合を取る。
- SES受信ルールが対象ドメイン宛メールを1st S3バケットに保存できるよう、SESドメイン検証・受信ルール設定は手動で済んでいる前提。

## Out of Scope（対象外）

- Route53のドメイン/レコード登録・SESドメイン検証（手動運用）。
- メール返信・自動応答・メールクライアント機能。
- 受信メールの全文検索・可視化ダッシュボード。
- スパム/ウイルススキャン等の高度なフィルタリング。
- presigned URL によるダウンロード提供（FR3.4 で不採用）。

## Open Questions（後続で扱う未決事項）
