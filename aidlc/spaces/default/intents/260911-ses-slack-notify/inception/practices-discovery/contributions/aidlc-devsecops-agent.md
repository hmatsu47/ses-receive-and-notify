## Contribution

DevSecOps（セキュリティ／サプライチェーン／パイプライン）の観点で、リードのドラフト（team-practices.md / discovered-rules.md / evidence.md）を独立にレビューした。本プロジェクトはグリーンフィールドの小規模 AWS サーバーレスツール（SES → S3 → Lambda デコード → 2nd S3 → Slack Webhook）で、単独開発・単独運用・手動デプロイ・relaxed change control、成功指標は「取りこぼしゼロ」の信頼性である。この文脈に即して、過剰なセキュリティ運用を課さずに defensible な最小限の統制を提案する。

### シークレット取り扱い（.env / シークレットマネージャ）

- リードの「設定値・Webhook URL は `.env` またはシークレットマネージャから読み込み、コード／IaC へハードコードしない」方針は妥当。ただし DevSecOps 観点で一段具体化を推奨する。
- Slack Webhook URL は「送信権限そのもの」を持つ機微値であり、S3 のオブジェクトに書かれたリンク・ログ・監査記録・Slack 本文に絶対に混入させない。Lambda 実行時は環境変数（暗号化）または SSM Parameter Store（SecureString）/ Secrets Manager から取得する構成を第一候補とする。`.env` はローカル開発・手動デプロイ時の投入経路に留め、デプロイ後のランタイムでは AWS 側のパラメータ管理に寄せる方針を推奨（言語・IaC 確定後に固定）。
- `.env` は必ず `.gitignore` 対象とし、`.env.example`（値はプレースホルダのみ）をリポジトリに置いて必要キー名だけを共有する。実値は決してコミットしない。

### Lint / Format / SAST

- リードの「リンタ／フォーマッタはプロジェクト設定へ委譲」は方向性として妥当。DevSecOps 観点では、静的解析にセキュリティ系ルールを最初から組み込むことを推奨する。
  - Python なら Ruff（セキュリティ系ルールセット有効化）＋ Bandit、TypeScript/Node なら ESLint に security プラグインを追加。
  - IaC を採用する場合（CDK/SAM/Terraform）は IaC 静的解析（Checkov / cfn-nag / cdk-nag のいずれか）を必須ラインとして推奨。特に S3 バケットの公開禁止・暗号化・IAM の過剰権限を検出させる。
- SAST はローカル・CI ともに「Critical/High はブロック、Medium は警告」の閾値を目安にする。小規模ツールのため導入コストを抑え、まずはリンタ内蔵のセキュリティルールから開始してよい。

### DAST

- 本ツールは公開 HTTP API を持たず、SES/S3 イベント駆動でありユーザー入力を受ける Web 面がない。よって従来型 DAST は費用対効果が低く、本スコープでは必須としない。
- 代替として「メール本文・ヘッダ・添付＝信頼できない外部入力（untrusted data）」として扱う入力検証・サニタイズを重視する。特に、デコードした本文・Subject を Slack ペイロードへ整形する際のインジェクション対策（Slack のメンション／リンク／制御文字の無害化、~200文字要約時の安全な切り詰め）を統制対象とすることを提案する。

### 依存関係・サプライチェーン

- 依存脆弱性スキャンを軽量に常設することを推奨（言語標準ツールで足りる）：Python は `pip-audit`、Node は `npm audit`。CI 上で Critical/High（既知エクスプロイトあり）をビルド失敗条件にする。
- 依存はバージョン固定（lockfile をコミット、range 依存を避ける）。Lambda ランタイムのランタイムバージョンも固定し、定期的にパッチ更新する。
- タイポスクワッティング対策として、見慣れないパッケージ名は導入前に確認する。GitHub 利用なら Dependabot を有効化し、月次程度の更新運用を目安とする。

### IAM 最小権限

- Lambda 実行ロールは最小権限で設計する。想定される最小境界を明記して統制化することを推奨：
  - 受信バケットに対する `s3:GetObject`（読み取り元プレフィックス限定）。
  - 保管先 2nd バケットに対する `s3:PutObject`（書き込み先プレフィックス限定）。
  - `logs:CreateLogStream` / `logs:PutLogEvents`（CloudWatch Logs）。
  - SecureString/Secret 取得が必要な場合は該当パラメータ ARN 限定の `ssm:GetParameter` / `secretsmanager:GetSecretValue`。
- ワイルドカード `Resource: *` や過剰なマネージドポリシー付与は禁止方向。SES → S3 の受信ルール、S3 バケットポリシー、KMS 復号権限も最小に絞る。

### データ保護（保管・転送）

- 2つの S3 バケットは暗号化（SSE-S3 か SSE-KMS）を有効化し、パブリックアクセスは全ブロックする。オブジェクトキーは「受信日時＋メッセージID」であり列挙可能性があるため、バケット公開禁止と署名付き URL 前提のアクセス設計を推奨。
- Slack 通知に載せる S3 リンクは、恒久公開 URL ではなく短命の署名付き URL、または閲覧者が別途認証してアクセスする形を推奨（本文の機微情報流出を避ける）。
- メール本文・添付には PII が含まれ得るため、CloudWatch Logs に本文全文やヘッダの機微部分を出力しない。ログはメタデータ（メッセージID、処理結果、エラー種別）中心とする。

### 監査・可観測性（セキュリティ側面）

- 失敗時のログ可視化方針（リードの Mandated）に加え、デコード失敗・添付上限超過・Slack 送信失敗を「区別可能な構造化イベント」としてログ化し、必要なら CloudWatch メトリクス／アラームで「取りこぼしゼロ」を監視できるようにすることを推奨（アラートは症状ベース：受信件数と通知成功件数の差分など）。
- API 資格情報や Webhook を扱う経路では、失敗時のエラーメッセージに内部情報（スタックトレース、シークレット、内部パス）を出さない。

### ヒアリングで確認すべきセキュリティ論点（ギャップ）

- シークレット格納先を `.env`（ランタイムも含む）で足りるとするか、SSM Parameter Store / Secrets Manager をランタイム標準にするか。
- 2nd バケットの保管データの保持期間・ライフサイクル（PII を含み得るため）と、暗号化に KMS CMK を使うか SSE-S3 で足りるか。
- Slack に載せる S3 リンクを署名付き URL とするか、恒久リンク＋別途認証とするか。
- SES/S3/Lambda が同一アカウントか別アカウントか（別アカウント連携時はクロスアカウント権限の最小化方針が変わる）。
- 依存脆弱性・IaC 静的解析を CI ゲート化するか、ローカル手動チェックに留めるか（単独運用の負荷とのバランス）。
