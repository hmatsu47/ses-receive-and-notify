## Contribution

品質（テスト戦略・カバレッジ・CI品質ゲート・信頼性経路のテスト設計）の観点から、リードのドラフトをレビューした。成功指標が「通知の取りこぼしゼロ」という信頼性である以上、テスト方針はこの一点に収束させるべきという立場で補強点を述べる。

### テスト方針（Testing Posture）への補強

- **methodology=test-after / ユニット中心の方針は妥当**。単独開発・稀受信・小規模の文脈では、常時起動の結合テスト基盤を用意しないという判断も合理的で、テストピラミッド（ユニット厚め・E2E最小）に沿う。ただし「取りこぼしゼロ」は本質的に境界・失敗系の話であり、happy path テストだけでは指標を守れない。重点経路には**失敗injection試験を必須**として明記することを提案する。
- **リトライ／冪等性のテストが最重要だが現ドラフトに明示がない**。Lambda は SES/S3 起因で再実行され得るため、同一メッセージIDの二重処理でも「2nd S3 の重複保管が壊れない」「Slack 通知が意図せず多重発火しない」ことをユニットで検証する必要がある。S3オブジェクトキー（受信日時＋メッセージID）を冪等キーとして機能させる設計前提を、テストで固定したい。
- **部分失敗の継続性テスト**（discovered-rules の Mandated「デコード/通知に失敗しても受信メールのS3保存は継続」に対応）。「デコード失敗 → 保存は継続」「Slack送信失敗 → 保存は継続・ログ可視化」を、それぞれ独立したユニットテストで担保する。これは Mandated 規則の受け入れテストそのものであり、規則1件につきテスト1件を対応付けることを提案する。
- **添付処理上限のテスト**（Forbidden「上限超過添付を強制デコードしない」に対応）。上限ちょうど／上限超過／未満の3点（境界値分析）でデコードスキップと保存・通知継続を検証する。

### カバレッジ・ツーリング

- 新規の数値カバレッジフロアを課さない判断は org スコープfloorに準拠しており支持する。ただし**重点経路（デコード・S3キー生成・要約整形・Slackペイロード整形・失敗ハンドリング）に限っては branch coverage を目視確認する運用**を推奨する。line coverage の数値目標ではなく「失敗分岐が1つ以上テストされているか」を品質ゲートの実質基準とする。
- ツールは言語確定後に固定（Python: pytest + coverage / responses・moto、Node: vitest|jest + aws-sdk-client-mock 等）で妥当。外部依存モックとして SES/S3 は `moto`（Python）や `aws-sdk-client-mock`（Node）、Slack Webhook は HTTP スタブという具体候補を evidence の不確実性項目に紐づけたい。

### CI 品質ゲート

- 手動デプロイ前提でも、**マージ前のローカル最低ゲート（lint＋ユニット全緑）をセルフレビューの明文チェックリストに含める**ことを提案する。「既存スイートをグリーンに保つ」を floor とする現方針を、セルフレビュー時に機械的に確認できる形にする。
- 将来 GitHub Actions 等を導入する場合に備え、テストは CI から無認証・ローカル実行可能（実AWS資格情報に依存しない＝モック前提）に保つことを規約化したい。

### ヒアリングで解消すべき品質観点のギャップ

- 「取りこぼしゼロ」の**検証可能な定義**：DLQ（SQS Dead Letter Queue）や Lambda リトライ回数、失敗時アラート（CloudWatch Logs 可視化のみか、閾値アラームまで要るか）の要否。テスト対象と受け入れ基準がこれで変わる。
- デコード対象メールの**代表サンプル**（multipart、日本語MIMEエンコード、添付あり/なし、上限超過添付）の入手可否。テストフィクスチャの現実性を左右する。
- Slack Webhook 障害時の**期待挙動**（無視してログのみか、リトライするか）。通知経路のテストケース分岐が決まる。
- 本文要約「冒頭200文字程度」の**正確な仕様**（文字数か表示幅か、マルチバイト境界の扱い、トリム位置）。整形ロジックの境界テストに必要。

## Positions

- AGREE: methodology=test-after、ユニットテスト中心、常時結合基盤を持たない方針（小規模・稀受信の文脈で妥当）。
- AGREE: 新規数値カバレッジフロアを課さず既存スイートのグリーン維持を floor とする方針（org スコープfloor準拠）。
- OBJECT: Testing Posture に、信頼性指標を守るための**冪等性／部分失敗継続／リトライの失敗injectionテストを必須**として明示すること、および**Mandated/Forbidden 各規則に受け入れテストを1対1で対応付ける**ことを追記すべき。現ドラフトは重点経路を挙げるに留まり、取りこぼしゼロを検証する具体的テスト種別（境界値・失敗系・冪等性）が規約として不足している。
